# Introduction

첫 번째 글에서 IP 주소 몇 개를 나열한 간단한 Inventory로 Ansible의 기본 동작을 확인했습니다. 하지만 실제 환경에서는 수십 개 이상의 호스트를 관리해야 하며, 각 호스트는 서로 다른 역할과 설정을 가집니다. 웹 서버, 데이터베이스 서버, 로드 밸런서가 각각 다른 설정을 필요로 하고, 개발 환경과 프로덕션 환경은 분리되어야 합니다. 이러한 복잡성을 효과적으로 관리하기 위해서는 Inventory의 기능들을 이해하고 활용해야 합니다.

# Understanding Inventory Structure

Ansible Inventory는 관리 대상 호스트의 목록과 설정을 담은 파일입니다. 기본 위치는 `/etc/ansible/hosts`이지만 프로젝트별로 별도의 Inventory 파일을 만드는 것이 권장됩니다.

![blog ui](/assets/img/posts/2026-01-18-ansible2/inventory.png) *https://kimalarm.tistory.com/78*


Inventory는 yaml와 YAML 두 가지 형식을 지원합니다. Kubespray를 포함한 많은 프로젝트들이 ini 형식을 사용하지만, 이 글에서는 yaml 형식을 사용합니다.

가장 간단한 형태는 호스트를 한 줄에 하나씩 나열하는 것입니다.

```yaml
192.168.10.10
192.168.10.11
web-server.example.com
```

호스트를 역할별로 그룹화하면 특정 그룹에만 작업을 수행할 수 있습니다. 그룹명은 대괄호로 감쌉니다.

```yaml
[webservers]
web1.example.com
web2.example.com

[databases]
db1.example.com
db2.example.com
```

한 호스트는 여러 그룹에 동시에 속할 수 있습니다.

```yaml
[webservers]
web1.example.com

[production]
web1.example.com
db1.example.com

[staging]
web2.example.com
```

중첩 그룹을 만들 때는 `:children` 키워드를 사용합니다.

```yaml
[webservers]
web1.example.com
web2.example.com

[databases]
db1.example.com

[production:children]
webservers
databases
```

반복적인 호스트 정의를 간소화할 수 있습니다.

```yaml
[webservers]
web[1:10].example.com        # web1, web2, ..., web10

[databases]
db[01:20].example.com         # db01, db02, ..., db20 (zero-padded)

[dns_servers]
dns[a:d].example.com          # dnsa, dnsb, dnsc, dnsd (alphabetical)

[compute_nodes]
192.168.4.[0:255]             # 192.168.4.0 to 192.168.4.255 (IP range)
```

# Organizing Hosts with Groups

[Ansible 공식 문서](https://docs.ansible.com/projects/ansible/latest/getting_started/get_started_inventory.html#tips-for-building-inventories)는 그룹을 구성할 때 What, Where, When 세 가지 관점을 고려할 것을 권장합니다.

- What: 호스트의 역할
- Where: 리전, 데이터센터 등 물리적/논리적 위치
- When: dev,prod와 같은 생명주기 단계

또한 그룹명은 아래와 같은 Naming Conventions를 가집니다.

- 공백, 하이픈 사용 금지
- 숫자로 시작하지 않기 (예: `19th_floor` → `floor_19`)
- 대소문자 구분됨
- 의미가 명확한 이름 사용

# Variables

변수를 사용하면 호스트별로 다른 설정을 적용할 수 있습니다.

## Host Variables

호스트명 옆에 변수를 정의합니다. `key=value` 형식을 사용하며, 공백으로 구분합니다.

```yaml
[webservers]
web1 ansible_host=192.168.10.10 ansible_port=22 ansible_user=ubuntu
web2 ansible_host=192.168.10.11 ansible_port=2222 ansible_user=centos
```

## Group Variables

그룹 전체에 공통 변수를 적용할 때는 `[groupname:vars]` 섹션을 사용합니다.

```yaml
[webservers]
web1 ansible_host=192.168.10.10
web2 ansible_host=192.168.10.11

[webservers:vars]
ansible_user=ubuntu
http_port=80
```

모든 호스트에 적용되는 변수는 `[all:vars]`에 정의합니다.

```yaml
[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

## Using group_vars and host_vars

변수가 많아지면 Inventory 파일이 복잡해집니다. 이때 group_vars와 host_vars 디렉터리를 사용하면 변수를 별도 파일로 분리할 수 있습니다.

`group_vars/all.yml`: 모든 호스트에 적용

```yaml
---
ansible_python_interpreter: /usr/bin/python3
```

`group_vars/webservers.yml`: webservers 그룹에만 적용

```yaml
---
http_port: 80
https_port: 443
max_clients: 200
```

`host_vars/web1.example.com.yml` - 특정 호스트만 적용

```yaml
---
ansible_host: 192.168.10.10
max_clients: 300
```

## Variable Precedence

위와 같이 Ansible은 여러 위치에서 변수를 정의할 수 있으며, 같은 이름의 변수가 여러 곳에 정의된 경우 명확한 우선순위 규칙에 따라 최종 값이 결정됩니다.Inventory 내에서의 변수 우선순위는 다음과 같습니다.

1. **Host Variables (host_vars)**: 특정 호스트에만 적용되는 변수로 가장 높은 우선순위를 가집니다.
2. **Group Variables (group_vars)**: 그룹에 속한 모든 호스트에 적용되며, 호스트 변수가 없을 때 사용됩니다.
3. **All Group Variables**: 모든 호스트에 기본값으로 적용되는 변수로 가장 낮은 우선순위를 가집니다.

Ansible Configuration
ansible.cfg 파일로 프로젝트 전체의 기본 설정을 관리합니다.
설정 파일 우선순위:

환경변수 ANSIBLE_CONFIG
현재 디렉터리의 ansible.cfg (프로젝트별 설정)
~/.ansible.cfg (사용자 설정)
/etc/ansible/ansible.cfg (시스템 전역 설정)

프로젝트 디렉터리에 ansible.cfg를 만들면 해당 디렉터리에서 실행되는 모든 명령이 이 설정을 따릅니다.
bashcat <<EOT > ansible.cfg
[defaults]
inventory = ./inventory
remote_user = root
host_key_checking = False

[privilege_escalation]
become = True
become_method = sudo
become_user = root
become_ask_pass = False
EOT
이제 -i 옵션 없이 명령을 실행할 수 있습니다.
bashansible all -m ping
ansible web -m shell -a "uptime"
Practical Example
Kubernetes 클러스터 배포를 위한 Inventory를 작성합니다.
bashmkdir -p inventory/group_vars
inventory/hosts:
bashcat <<EOT > inventory/hosts
[all]
tnode1 ansible_host=10.10.1.11 ip=10.10.1.11
tnode2 ansible_host=10.10.1.12 ip=10.10.1.12
tnode3 ansible_host=10.10.1.13 ip=10.10.1.13

[kube_control_plane]
tnode1

[etcd]
tnode1

[kube_node]
tnode2
tnode3

[k8s_cluster:children]
kube_control_plane
kube_node

[all:vars]
ansible_python_interpreter=/usr/bin/python3
EOT
inventory/group_vars/all.yml:
bashcat <<EOT > inventory/group_vars/all.yml
---
cluster_name: my-k8s-cluster
kube_version: v1.28.5
bin_dir: /usr/local/bin
EOT
inventory/group_vars/k8s_cluster.yml:
bashcat <<EOT > inventory/group_vars/k8s_cluster.yml
---
kube_service_addresses: 10.233.0.0/18
kube_pods_subnet: 10.233.64.0/18
EOT

Conclusion
Inventory는 단순한 호스트 목록이 아니라 인프라의 구조와 설정을 표현하는 설계도입니다. 그룹을 통해 호스트를 조직하고, 변수로 설정을 관리하며, ansible.cfg로 프로젝트 전체를 통합했습니다.
하지만 지금까지 다룬 것은 정적 Inventory입니다. 클라우드 환경처럼 호스트가 자주 생성되고 삭제되는 동적 환경에서는 다른 접근이 필요합니다. 다음 글에서는 Dynamic Inventory를 다룹니다. AWS, GCP 같은 클라우드 프로바이더의 API를 통해 실시간으로 인스턴스 목록을 가져오는 방법을 학습할 예정입니다.
